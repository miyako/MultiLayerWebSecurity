# Sentinel：HTTPリクエストハンドラーとHTTPルールを使用した多層Webセキュリティアーキテクチャ

Anouar Moustarih（Quality Support Engineer、4D Morocco）

テクニカルノート26-05

## 概要

Sentinelは、4D v21.0 LTSの2つの機能、HTTPリクエストハンドラー（HTTP Request Handlers）とHTTPルール（HTTP Rules）を、本番運用レベルのWebセキュリティアーキテクチャの基盤としてどのように活用できるかを示す4Dのデモアプリケーションです。HTTPリクエストハンドラーはURLパターンを型付きのクラス関数に結び付け、ルーティングとビジネスロジックを明確に分離します。一方、HTTPルールはアプリケーションのコードに手を加えることなく、状況に応じたセキュリティ用のレスポンスヘッダーを挿入します。Sentinelはこれらの基本機能の上に、受信したすべてのリクエストをコストの低い順に評価する11段階のゲートからなる防御パイプライン（defense pipeline）を実装しています。許可リストとブロックリストの照合が最初に実行され、WAFのパターンマッチングやレート制限など計算負荷の高いチェックは最後に実行されます。パイプラインは、CPUとトラフィックを契機とするパニックモード、ヘッダー異常の拒否、パストラバーサル・SQLインジェクション・クロスサイトスクリプティングのペイロードを正規表現で検出するWAFスキャン、自動化された偵察に対するハニーポットによる欺瞞、そしてIP単位およびグローバルのスライディングウィンドウ方式によるレート制限を網羅しています。パイプラインを補完するSonar侵入検知・防止システムは、User-Agentヘッダーの欠落、ツール系クライアント、偽装ブラウザー、既知の攻撃パターンといった行動シグナルを加算して各リクエストをスコアリングし、高スコアのリクエストは即時ブロックを行うスナイパーキューへ、低スコアのリクエストはパターン相関分析のためにアーカイブへ振り分けます。認証は専用のSentinelAuthクラスが担当し、bcryptでハッシュ化された静的パスフレーズまたは使い捨ての動的パスフレーズ（Dynamic Passphrase）を検証するとともに、IP単位のブルートフォース攻撃対策としてロックアウトを実施します。すべての実行時の状態は、アトミック書き込みパターンによってプロジェクトのDataフォルダー内のJSONファイルに保存され、設定はサーバーを再起動せずにホットリロードされます。フレームワークを使用しないJavaScript（vanilla JavaScript）で作成されたダッシュボードでは、リアルタイムのテレメトリ、防御トグル、攻撃シミュレーター、ワーカーの稼働状況を確認できます。

## はじめに

現代のWebサーバーは、認証情報に対するブルートフォース攻撃、大量のリクエストによるサービス拒否（DoS）攻撃、インジェクション攻撃、設定ミスのあるパスを探るスキャナーによる組織的な偵察など、幅広い自動化された脅威にさらされています。これらの脅威に個別のアドホックなコードで対処すると、ロジックが散在し、監査が困難になります。Sentinelは別のアプローチを取ります。4D v21.0 LTSで導入された2つの宣言的なセキュリティ機能、HTTPリクエストハンドラーとHTTPルールを構造上の基盤として使用し、その上に防御モジュールを単一の順序付きパイプラインとして重ねます。

このテクニカルノートでは、このアーキテクチャのすべての層を順に解説します。まず、IPリストの管理やレート制限のトークンバケットから、ワーカーのライフサイクル、アラートのエスカレーションまで、それぞれ独立した役割を担う16個の共有シングルトンクラスと、それらを動かすバックグラウンドワーカーを紹介します。次に、パイプラインに配置された9つの防御手法のそれぞれについて、対処する攻撃と、デモアプリケーションでの具体的な適用方法を説明します。「防御パイプライン」の章では、11段階のゲートの実行順序と、通常時およびパニック時の各ゲートの動作を記載しています。「Sonar」の章では、加算方式のスコアリング基準、スナイパーキューとドローンキューの振り分けのしきい値、エンジンの状態を公開する3つの管理用エンドポイントについて詳しく説明します。「HTTPHandlers.jsonとHTTPRules.json」の章では、完全なスキーマ、登録されているすべてのルート、そしてレスポンスヘッダーとそれぞれのヘッダーが軽減する脅威をルールごとに解説します。最後に、設定の永続化、ホットリロードの仕組み、ダッシュボードのポーリング間隔、ワーカーのオーケストレーションと終了シーケンスを取り上げます。

## 前提知識

本ドキュメントを読み進めるにあたり、以下の基本的な知識があることを前提としています。

- 共有シングルトンクラス
- HTTPの基礎（メソッド、ヘッダー、ステータスコード）
- JSONの構文と基本的な正規表現
- 一般的なWeb攻撃の種類（サービス拒否、SQLインジェクション、パストラバーサル、ヘッダーオーバーフロー）

## 動作要件

デモアプリケーションの全機能を試すには、以下の条件が満たされている必要があります。

- **4Dのバージョン**：21.0 LTS以降
- **ネットワーク**：ポート8044が開いており、ローカルのファイアウォールやネットワークのセキュリティポリシーによってブロックされていないこと
- **デモアプリケーション**：ホストコンピューターのlocalhostアドレス（127.0.0.1）とローカルネットワークアドレス（LANまたはWAN）の両方が許可リスト（allowlist）に登録されていること

**例：**

```json
"allowlist": {
    "127.0.0.1": "Manual",
    "192.168.XXX.YY": "Manual or via Dashboard"
}
```

> **重要**：IP BlacklistパネルのClear Allボタンをクリックすると、ip_lists.jsonファイルの内容が空になります。その場合は、127.0.0.1をはじめとする必要なアドレスを、手動またはダッシュボードの許可リストボタンから再登録する必要があります。

> **バグACI0106333（Windows固有）**：Windowsでは、Process activity.processes[0].cpuUsageがmacOSと比べて過大な値を返します。このテレメトリの差異によりCPUパニックゲートが作動し、受信リクエストがHTTP 503ステータスで拒否されます。現在修正中であり、修正を含むバージョンが提供され次第お知らせします。macOSには影響ありません。

## アーキテクチャの概要

### プロジェクトの共有シングルトンクラス

**DoSGuard**：11段階のゲートからなる防御パイプラインを管理します。On Web AuthenticationデータベースメソッドのエントリーポイントとしてauthenticateRequestを、また公開用のハンドラーから呼び出されるクラス関数として_gateを公開します。

**Sentinel**：40以上のエンドポイントからなる管理用HTTP APIを実装します。ステータス、トグル、攻撃、パニック、ハニーポット、ワーカー、Sonar、ダッシュボードのCRUD用のクラス関数が含まれます。

**SentinelAuth**：ログイン、ログアウト、認証状態の確認、ブルートフォース攻撃に対するロックアウト、動的パスフレーズの生成を管理します。bcryptでハッシュ化された静的パスフレーズを検証します。

**Sonar**：侵入検知・防止エンジンです。受信した各リクエストを0から100の範囲でスコアリングし、高スコアのリクエストをスナイパーキューへ、低スコアのリクエストをドローンキューへ振り分けます。

**Honeypot**：おとりのURLパスへのリクエストを検知します。アクセスを記録し、送信元IPを24時間禁止したうえで、CRITICALアラートを発行します。

**IPManager**：ブロックリスト、許可リスト、ストライクカウンターを管理します。アトミック書き込みによってData/ip_lists.jsonに保存します。

**ConfigManager**：実行時の設定ストアを管理します。アトミック書き込みパターンでData/dosguard_config.jsonの読み書きを行います。

**RequestLogger**：メモリ上のリクエストログを管理します。2,000件のリングバッファーで、定期的にディスク上の日次JSONLファイルへフラッシュします。

**AlertManager**：しきい値に基づくアラートを管理します。INFO、WARNING、CRITICALのイベントを発行し、アラートキーごとに60秒のクールダウンを設けます。

**ProcessOrchestrator**：ワーカーのライフサイクルを管理します。起動時にワーカーを生成し、終了時にシャットダウン信号を全ワーカーに送信し、Workersパネル用にハートビートを追跡します。

**RulesManager**：ダッシュボードからHTTPRules.jsonへのCRUDアクセスを提供します。ホットリロードのためにディスク上のバージョンを保持します。

**HandlersManager**：ダッシュボードからHTTPHandlers.jsonへのCRUDアクセスを提供します。ホットリロードのためにディスク上のバージョンを保持します。

**HeaderValidator**：受信したリクエストのヘッダーを検証します。ヘッダーサイズ、NULLバイト、CRLFインジェクションの試みをチェックします。

**FileUploadHandler**：ファイルアップロードのリクエストを処理します。入力をサニタイズし、防御チェックのために_gateクラス関数へ転送します。

**URLNormalizer**：WAFが検査する前に、受信したURLを正規形に変換します。

**URLCodec**：多重エンコードによる回避を防ぐため、複数回のパーセントデコードを行います。

### プロジェクトメソッド

**CPUMonitor_Worker**：プロセスのCPU使用状況を1秒間隔でサンプリングします。CPU使用率が設定されたしきい値を超え続けると、CPUパニックフラグを立てます。

**PanicWatchdog_Worker**：グローバルなリクエストレートを5秒間隔で監視します。レートが解除しきい値を下回ると、トラフィックパニックモードを自動的に解除します。

**LogFlusher_Worker**：RequestLoggerのリングバッファーを、約5秒間隔でディスク上の日次ログファイルへフラッシュします。

**HoneypotSweeper_Worker**：期限切れのハニーポットによる禁止を60秒間隔で解除します。ハニーポットによる禁止は24時間続きます。

**Sonar_Sniper_Worker**：スナイパーキューを1秒間隔で処理します。送信元IPを1時間ブロックし、ブロック1件ごとにData/sonar_kills.jsonlへ1行追記します。

**Sonar_Drone_Worker**：ドローンキューを10秒間隔で処理します。送信元IPをブロックせずに、リクエストをData/sonar_archive.jsonlにアーカイブします。

**Attack_CPUArmageddon**：内部の攻撃シミュレーターです。ワーカースレッドから/heavyに大量のリクエストを送り、CPU使用率をパニックしきい値以上に押し上げます。

**Attack_Bandwidth**：内部の攻撃シミュレーターです。偵察やトラバーサルのプローブを含む複合的なトラフィックを発生させ、レート制限とWAFを検証します。

**Attack_HeaderOverflow**：内部の攻撃シミュレーターです。サイズ超過、不正な形式、CRLFインジェクションを含むヘッダーを送信し、HeaderValidatorを検証します。

**Attack_GhostFlood**：内部の攻撃シミュレーターです。50個のIPから分散型の大量リクエストを送り、グローバルなレート制限と、ブロックリストへの自動昇格ロジックを検証します。

**Startup**：共有シングルトンクラスを初期化し、ディスク上の設定を読み込み、ワーカーをProcessOrchestratorに登録して、Webサーバーを起動します。

### データベースメソッド

**On Startup**：4Dプロジェクトを開いたときに1回だけ実行されます。新しいプロセスでStartupプロジェクトメソッドを起動します。

**On Web Authentication**：受信した各HTTPリクエストに対して、ルートの照合前に実行されます。Sonar.intercept、次にDoSGuard.authenticateRequestを実行し、セッションの権限を設定します。

**On Exit**：4Dプロジェクトを閉じるときに実行されます。まずWebサーバーを停止し、次にすべてのワーカーにシャットダウンを通知し、登録済みの各ワーカーに対してKILL WORKERを実行します。

## 防御手法

この章では、デモアプリケーションで使用しているすべての防御手法を、一般的なWebセキュリティの概念として説明します。実装の詳細は後続の章で扱います。以下の各手法について、防御の内容、対処する攻撃、デモアプリケーションでの適用方法を示します。

### 認証とブルートフォース攻撃対策

認証（authentication）は、特権的なアクセスを許可する前にクライアントの身元を確認します。ブルートフォース攻撃対策は、1つの送信元が一定時間内に認証に失敗できる回数に上限を設けます。認証だけではパスワードの推測を防げないため、この2つの対策は組み合わせて使用します。

対処する攻撃：攻撃者が既知のアカウントに対して多数のパスワードを試すブルートフォース攻撃。また、他のサービスから漏洩したパスワードを使用するクレデンシャルスタッフィング（credential stuffing）。

デモアプリケーションでの適用方法：SentinelAuthクラスが、bcryptでハッシュ化された静的パスフレーズ、または使い捨ての動的パスフレーズを検証します。15分以内にログインに5回失敗すると、送信元IPは30分間ロックアウトされます。ロックアウトの状態はメモリ上にのみ保持されます。

### IP許可リストとブロックリスト

許可リスト（allowlist）は、防御チェックを通過させる送信元IPアドレスのリストです。ブロックリスト（blocklist）は、すべてのアクセスを拒否する送信元IPアドレスのリストです。許可リストは管理者の端末や信頼できる監視ツールに、ブロックリストは攻撃者や常習的な不正利用者に使用します。

対処する攻撃：いずれかの防御層で攻撃者が特定されると、ブロックリストによってその攻撃者はそれ以上アクセスを続けられなくなります。ストライクカウンターにより、違反を繰り返す送信元は恒久的にブロックされます。

デモアプリケーションでの適用方法：IPManagerクラスが両方のリストを管理します。リストはアトミック書き込みによってData/ip_lists.jsonに保存されます。ダッシュボードから手動で編集できます。ストライクカウンターが5回に達すると、一時的なブロックが恒久的なブロックに昇格します。

### レート制限

レート制限（rate limiting）は、1つの送信元が一定時間内に送信できるリクエスト数を制限します。一般的に2つの種類があります。IP単位のレート制限は送信元アドレスごとに個別に追跡し、グローバルなレート制限はすべての送信元を合計したトラフィックを追跡します。

対処する攻撃：サーバーが処理できる以上のリクエストを送信してリソースを枯渇させる大量リクエスト攻撃。サービス拒否のフラッド攻撃、ログインのブルートフォース攻撃、クレデンシャルスタッフィングのキャンペーンなどが含まれます。

デモアプリケーションでの適用方法：IP単位のトークンバケットにより、各送信元は1分あたり100リクエスト、5秒間のバーストあたり20リクエストに制限されます。グローバルな集計カウンターにより、全体のトラフィックは1分あたり10,000リクエストに制限されます。上限を超えると一時的にブロックされ、ストライクカウンターが加算されます。

### ヘッダーの検証

HTTPヘッダーの検証では、ヘッダーが妥当なサイズを超えている、NULLバイトを含む、あるいはCRLF（キャリッジリターン + ラインフィード）シーケンスを含むリクエストを拒否します。このようなヘッダーは、通常、最初のリクエストの中に2つ目のリクエストを紛れ込ませようとする試みです。

対処する攻撃：サイズの大きいヘッダーでサーバーをクラッシュさせようとするヘッダーオーバーフロー攻撃。文字列処理を途中で打ち切らせようとするNULLバイト攻撃。追加のヘッダーを挿入したり、リクエストを2つに分割したりしようとするCRLFインジェクション。

デモアプリケーションでの適用方法：HeaderValidatorクラスが、ヘッダーサイズを設定された上限（デフォルトは8,192バイト）と照合します。また、NULLバイトや不正なCRLFシーケンスを含むヘッダーも拒否します。違反したリクエストにはHTTP 400が返され、送信元IPは300秒間ブロックされます。

### Webアプリケーションファイアウォール（WAF）

Webアプリケーションファイアウォール（Web Application Firewall）は、HTTPリクエストをアプリケーションのコードに渡す前に、既知の攻撃パターンがないかを検査します。WAFは悪意のあるパターンのリストを保持しており、パターンに一致したリクエストはHTTP 403レスポンスで拒否されます。

対処する攻撃：URLのパラメーターやパスに悪意のあるペイロードを埋め込むインジェクション攻撃。パストラバーサル、SQLインジェクション、クロスサイトスクリプティング、コマンドインジェクション、evalを利用したコード実行などが含まれます。

デモアプリケーションでの適用方法：DoSGuardクラス内のWAFが、リクエストURLに含まれるパストラバーサルのシーケンス、evalの呼び出し、scriptタグ、union selectのSQL断片、SQLインジェクションの末尾記号を検査します。一致した場合は該当するカテゴリーとともに403を返します。拒否するたびに送信元IPのストライクが1つ加算されます。

### ハニーポットURL

ハニーポットURL（honeypot URL）は、サーバーが実際には提供していないおとりのパスです。正規のクライアントがこれらのパスにリクエストすることはありません。リクエストしてきたクライアントは、悪意のあるクライアントまたは自動スキャナーとして扱われます。サーバーはアクセスを記録し、送信元を禁止します。

対処する攻撃：攻撃者（多くの場合はボット）が、/.env、/.git/config、/wp-admin、/admin.phpなどの既知の機密パスを探る偵察攻撃。こうしたパスが見つかることは、セキュリティ対策の不十分なサーバーの設定ミスを示しています。

デモアプリケーションでの適用方法：約12個のハニーポットURLがHTTPHandlers.jsonにルートとして登録されており、それぞれHoneypot.handleProbeに対応付けられています。アクセスがあるとCRITICALアラートが記録され、送信元IPは24時間禁止されます。

### 侵入検知と侵入防止（IDS / IPS）

侵入検知システム（Intrusion Detection System：IDS）は、トラフィックに悪意のある活動の兆候がないかを検査し、アラートを発行します。侵入防止システム（Intrusion Prevention System：IPS）はさらに踏み込み、問題のあるリクエストや送信元をブロックします。現代のシステムは、両方の役割を1つのエンジンにまとめています。

対処する攻撃：単一のパターンには一致しないものの、複数の弱いシグナルを示す標的型攻撃。スクリプトによるスキャンのキャンペーン、クレデンシャルスタッフィング、nmapやsqlmapなどのツールによる偵察が含まれます。

デモアプリケーションでの適用方法：Sonarクラスが、加算方式のシグナルに基づいて各リクエストに0から100のスコアを付けます。スコアが80以上の場合は即座に1時間ブロックします（IPSの動作）。スコアが1から79の場合は相関分析のためにアーカイブします（IDSの動作）。

### パニックモード

パニックモード（panic mode）は、サーバーが通常のトラフィックの処理を停止し、少数の許可リストからのリクエストのみを受け付ける緊急状態です。CPU、メモリ、トラフィック量が、運用者が危険と判断するしきい値を超えた場合の最終手段として使用します。

対処する攻撃：送信元の多様さによってIP単位のレート制限をすり抜ける分散型のフラッド攻撃。また、不正な動作をするクライアントや内部のバグによってリソースが飽和する状況にも対応します。

デモアプリケーションでの適用方法：CPUMonitor_WorkerがプロセスのCPU使用率を1秒間隔でサンプリングします。CPU使用率が85%以上の状態が30秒続くとパニックモードが作動し、50%を下回ると解除されます。運用者はダッシュボードから手動でパニックモードを作動・解除することもできます。

### 厳格なレスポンスヘッダー

厳格なレスポンスヘッダーは、レスポンスを安全に表示する方法をブラウザーに指示します。一般的なヘッダーには、Content-Security-Policy（実行を許可するスクリプト）、X-Content-Type-Options（MIMEタイプを推測しない）、X-Frame-Options（フレーム内への埋め込みを許可しない）、Referrer-Policy（リファラー情報の漏洩を制限する）などがあります。

対処する攻撃：クロスサイトスクリプティング（XSS）、クリックジャッキング、MIMEスニッフィング攻撃、Refererヘッダーを介した情報漏洩。

デモアプリケーションでの適用方法：すべてのレスポンスに、HTTPRules.jsonのキャッチオールルールによって基本ヘッダーが付与されます。特定のルートには、より厳格なヘッダーが追加されます。ルートごとのポリシーの詳細は、本テクニカルノートの「HTTPHandlers.jsonとHTTPRules.json」の章に記載しています。

## 防御パイプライン

### 実行順序

DoSGuard.authenticateRequestは、順序の決まった11のチェックを実行します。最初に判定を下したチェックでパイプラインは終了します。

この順序は意図的なものです。コストが低く判定が明確なチェックを先に実行し、コストの高いチェック（WAF、レート制限）を最後に実行します。

| ゲート | チェック | 一致した場合の動作 |
|---|---|---|
| 1 | マスターゲート（defenses.master） | OFFの場合は即座に受け付け、以降のチェックは行わない。 |
| 2 | CPUパニックフラグ | 許可リストにないIPを503で拒否する。 |
| 3 | トラフィックパニックフラグ | 許可リストにないIPを503で拒否する。期限切れで自動解除。 |
| 4 | ヘッダーサイズの上限（デフォルトは8192バイト） | 400で拒否する。送信元IPを300秒間ブロックする。 |
| 5 | ハンドラーの防御トグル | OFFの場合は受け付け、一致したハンドラーにリクエストを転送する。 |
| 6 | IP許可リスト | 受け付ける。残りのゲートをスキップする。 |
| 7 | IPブロックリスト | 403で拒否する。 |
| 8 | ハニーポットURLとの一致 | アクセスを記録する。403のおとり用レスポンス本文の生成はハンドラーに任せる。 |
| 9 | WAF（URLNormalizer + URLCodec） | トラバーサル、eval、script、SQLiを検出した場合は403で拒否する。 |
| 10 | IP単位のスライディングウィンドウ方式のレート制限 | 429で拒否する。ストライクを加算する。バースト時はブロックする。 |
| 11 | グローバルなレート制限 | 429で拒否する。アラートを発行する。 |

### マスターゲートの動作

マスターゲートは最初のチェックです。defenses.masterがfalseの場合、パイプラインは即座にリクエストを受け付け、パニックを含む以降のすべてのチェックをスキップします。

マスターゲートがOFFの状態でも、CPUモニターとパニックウォッチドッグはフラグを更新し続けます。そのため、ダッシュボードのパニックインジケーターがACTIVEと表示されていても、実際には何も適用されていない場合があります。マスターゲートがOFFの間、このインジケーターは表示上のものにすぎません。

### IP単位のスライディングウィンドウ方式のレート制限

各送信元IPには、2つのウィンドウを持つトークンバケットが割り当てられます。長いウィンドウは60秒、バーストウィンドウは5秒です。

デフォルト値：1分あたり100リクエスト、5秒間のバーストあたり20リクエスト。上限を超えた場合は300秒間ブロック。ストライクが5回に達すると恒久的にブロック。

デフォルト値はData/dosguard_config.jsonに保存されており、ダッシュボードから編集できます。

### グローバルなレート制限

1つの集計カウンターが、直近1分間にすべてのIPから受け付けたリクエストの総数を追跡します。デフォルトの上限は10,000リクエストです。

上限を超えると、リクエストには429が返され、アラートが発行されます。上限の50%に達した時点で事前のWARNINGが発行されるため、運用者は上限に達する前に増加の傾向を把握できます。

### パニックモード

パニックモードでは、許可リストにない送信元からのすべてのリクエストをHTTP 503で拒否します。このモードはCPUモニターによって自動的に、またはダッシュボードから手動で作動します。

CPU使用率が85%以上の状態が30秒続くと、CPUパニックが自動的に作動します。CPU使用率が最小継続時間にわたって50%を下回ると、このモードは解除されます。

許可リストに登録されたIP（管理者の端末など）はパニックモードの影響を受けず、ダッシュボードに引き続きアクセスできます。

## Sonar IDS / IPS：スコアリング、スナイパー、ドローン

### 目的

Sonarは、On Web Authenticationデータベースメソッドの実行後にすべてのリクエストを検査します。検査の結果、0から100の整数のスコアが算出されます。

スコアによって、リクエストは2つのキューのいずれかに振り分けられます。高スコアのリクエストは即座に措置の対象となり、低スコアのリクエストはパターン相関分析のためにアーカイブされます。

### スコアリング基準

スコアは加算方式で、上限は100です。各シグナルがポイントを加算し、最終的なスコアによって振り分け先が決まります。

| シグナル | ポイント |
|---|---|
| User-Agentヘッダーがない | +30 |
| ブロック済みのIPが再びアクセスしてきた | +80 |
| URLにパストラバーサルの「../」を含む | +50 |
| URLに「eval(」を含む | +50 |
| URLに「&lt;script」を含む | +50 |
| URLに「union select」を含む | +50 |
| URLに「'--」または「";--」を含む（SQLiの末尾記号） | +50 |
| ツールのUA：curl、postman、wget、python-requests、go-http-client、powershell | 各+25 |
| 偽装ブラウザー：Sec-Fetch-\*ヘッダーまたはSec-Ch-UaヘッダーのないMozilla UA | +60 |
| ボットのUA：googlebotまたはbingbot | +50 |
| 一般的なボットのUA：crawlerまたはspider | +40 |

### キューへの振り分け

振り分けはスコアの範囲によって決まります。しきい値は80です。

- スコアが80以上：リクエストはスナイパーキュー（上限500件）に入ります。Sonar_Sniper_Workerがキューを処理し、1時間のブロックを実施して、Data/sonar_kills.jsonlに1行書き込みます。
- スコアが1から79：リクエストはドローンキュー（上限2000件）に入ります。Sonar_Drone_Workerはブロックを行わずに、リクエストをData/sonar_archive.jsonlにアーカイブします。
- スコアが0：リクエストはキューに入りません。intercepted（検査件数）カウンターは加算されます。

### マスターゲートとの関係

マスターゲートがOFFの場合、Sonarは処理を省略します。interceptedカウンターは加算されますが、スコアリングやキューへの登録は行われません。

### 管理用エンドポイント

3つの管理用エンドポイントでSonarの状態を確認できます。いずれもsentinelAdmin権限が必要です。

- /admin/sonar/stats：現在のカウンターと最後に記録されたスコア
- /admin/sonar/queue：処理待ちのキュー項目（最大50件）
- /admin/sonar/archive：ドローンのアーカイブの最新200件

## 認証と動的パスフレーズ生成

### ログインの流れ

ダッシュボードの認証はSentinelAuth.handleLoginが処理します。このクラス関数は、3種類の認証情報を順にチェックします。

- **保留中の動的パスフレーズ生成（Dynamic Passphrase Generation：DPG）プール**：IPごとに発行されるコードで、生成後5分間有効です。
- **有効なDPG**：管理者に表示される一時的なパスフレーズです。
- **静的パスフレーズ**：dosguard_config.jsonのauth.dashboardPassphraseに保存されたbcryptハッシュです。

### ブルートフォース攻撃対策

SentinelAuthは、IPごとのログイン失敗回数を15分間のウィンドウで追跡します。5回失敗すると、そのIPは30分間ロックアウトされます。

### 権限の階層

デモアプリケーションでは、Project/Sources/roles.jsonに2つの権限（privilege）、sonarとsentinelAdminを定義しています。これに4D組み込みのguestを加えた3つの権限が、弱いものから強いものへと入れ子になっています。

| 権限 | 付与される対象 | 範囲 |
|---|---|---|
| guest | 受信したすべてのリクエスト | 公開のヘルスチェック、ハニーポットのプローブ、ファイルアップロード。 |
| sonar | すべてのリクエストに対してOn Web Authenticationデータベースメソッドが設定 | DoSGuardとHoneypotのハンドラー用クラス関数。 |
| sentinelAdmin | SentinelAuth.handleLoginのみが付与 | ダッシュボードのすべてのCRUD、パニック、攻撃シミュレーション。 |

### 動的パスフレーズ生成

DPGは、緊急時にダッシュボードへアクセスするための使い捨てのログイン認証情報を提供します。この仕組みにより、インシデント対応中に長期間有効な静的パスフレーズを保存したり共有したりせずに済みます。

DPGの生成は/admin/auth/generate-passphraseで公開されており、IPごとに1分あたり10回までにレート制限されています。

DPGを開始する4Dのクラス関数の呼び出し例を以下に示します。

```4d
$response:=cs.SentinelAuth.me.handleGeneratePassphrase($request)
```

## HTTPHandlers.jsonとHTTPRules.json

### Webセキュリティ用語集

以下の用語は、この章全体で使用します。

| 用語 | 定義 |
|---|---|
| User-Agent（UA） | クライアントのソフトウェアを識別するHTTPリクエストヘッダー。ブラウザー、curl、Postman、検索エンジンのクローラー、スクリプトによるクライアントは、それぞれ固有のUA文字列を送信する。Sonarクラスはこのヘッダーを解析してクライアントを分類する。 |
| Content-Security-Policy（CSP） | ページが読み込みを許可されるスクリプト、スタイル、フォント、画像、フレームをブラウザーに指示するレスポンスヘッダー。厳格なCSPは、ほとんどのクロスサイトスクリプティング攻撃を防ぐ。 |
| Cross-Origin Resource Sharing（CORS） | ブラウザーが異なるオリジンでホストされているサーバーからデータを取得できるようにする仕組み。Access-Control-Allow-\*レスポンスヘッダーと、OPTIONSのプリフライトリクエストによって制御される。 |
| ハニーポットURL | デモアプリケーションが実際には提供していないおとりのパス。このパスにリクエストしたクライアントは悪意のあるものとして扱われ、24時間禁止される。 |
| パストラバーサル | URL内の「../」シーケンスを使用して、意図したディレクトリの外にあるファイルを読み取る攻撃手法。WAFはこのシーケンスを含むURLをすべて拒否する。 |
| SQLインジェクション（SQLi） | URLパラメーターを介してクエリにSQLの断片を注入する攻撃。WAFは「union select」などのトークンや、「'--」や「";--」などの末尾記号を検出する。 |
| MIMEスニッフィング | サーバーが宣言したContent-Typeを信頼せずに、レスポンスのコンテンツタイプを推測するブラウザーの動作。「X-Content-Type-Options: nosniff」ヘッダーでこの動作を無効にできる。 |
| クリックジャッキング | 悪意のあるページが標的のサイトをフレーム内に隠し、エンドユーザーにフレーム内のページをクリックさせる攻撃。「X-Frame-Options: DENY」ヘッダーでこれを防げる。 |
| Referrer-Policy | ページからリンクをたどる際に、ブラウザーがRefererヘッダーで送信する内容を制御するレスポンスヘッダー。サードパーティのサイトへの情報漏洩を抑える。 |
| Permissions-Policy | ページが必要としないブラウザーの機能（カメラ、マイク、位置情報など）を無効にするレスポンスヘッダー。クロスサイトスクリプティングが発生した場合の攻撃対象領域を縮小する。 |

### HTTPリクエストハンドラー：公式の定義

4D Doc Centerより：HTTPリクエストハンドラーを使用すると、開発者は特定のHTTPリクエストをアプリケーション内のコードで処理できます。各ハンドラーは、URLパターンをクラス関数に結び付けます。設定はProject/Sources/HTTPHandlers.jsonに記述します。

### HTTPHandlers.jsonのスキーマ

HTTPHandlers.jsonはJSON配列です。各エントリーが、ルーティング可能なURLパターンを1つ記述します。

必須のキーはregexPattern、verbs、class、methodです。省略可能なキーはcommentです。

有効なエントリーの最小構成は、以下の例のとおりです。

```json
{
    "regexPattern": "^/admin/status$",
    "verbs": "GET",
    "class": "Sentinel",
    "method": "handleStatus"
}
```

4Dは配列を宣言順に評価し、最初に一致したregexPatternが採用されます。どのパターンにも一致しなかったURLは、On Web Connectionデータベースメソッドに渡されます。

### 4DがHTTPHandlers.jsonを評価するタイミング

4D WebサーバーはHTTPHandlers.jsonを起動時に読み込み、ディスク上のファイルが置き換えられるたびに再読み込みします。再起動は必要ありません。

実行時の評価順序：TLSの終端、On Web Authentication、ハンドラーの照合、クラス関数の呼び出し、HTTPRules.jsonによるヘッダーの挿入、レスポンスの順です。

### HTTPメソッドと権限

verbs文字列には、GET、POST、PUT、DELETE、OPTIONS、HEAD、PATCHを任意に組み合わせて指定できます。記載されていないメソッドのリクエストには405が返されます。

権限はHTTPHandlers.jsonでは宣言しません。権限はroles.jsonで、クラス名またはクラス関数名に対して宣言します。この2つのファイルが連携して機能します。

### デモアプリケーションでのHTTPHandlers.jsonの使用方法

デモアプリケーションには58のルートが登録されています。ルートはURLのプレフィックスによってカテゴリーに分類されています。

| カテゴリー | パターンのプレフィックス | クラス | ルート数 |

### HTTPルール

HTTPルールを使用すると、開発者はHTTPレスポンスヘッダーを追加することで、HTTPレスポンスのセキュリティポリシーを定義できます。設定はProject/Sources/HTTPRules.jsonに記述します。

### HTTPRules.jsonのスキーマ

HTTPRules.jsonはJSON配列です。各エントリーは、正規表現によるセレクターと、ヘッダーのセットで構成されます。

必須のキーはregexPatternとresponseHeadersです。requestHeadersとresponseHeadersのどちらかを指定できます。

すべてのURLにセキュリティヘッダーを追加する基本ルールを以下に示します。

```json
{
    "regexPattern": "^/.*$",
    "responseHeaders": {
        "X-Content-Type-Options": "nosniff",
        "X-Frame-Options": "DENY",
        "Referrer-Policy": "strict-origin"
    }
}
```

| ^/$ | ルートURL（パスなし） | Content-Security-Policy: 上記のダッシュボードのページのルールと同じ。Cache-Control: no-cache, must-revalidate. X-Robots-Tag: noindex, nofollow. | ルートURLはダッシュボードのページと同様に扱われ、同じ厳格なCSPが適用される。検索エンジンにはこのURLを無視するよう指示する。 |

### レスポンスヘッダー用語集

HTTPRules.jsonで使用されているすべてのHTTPレスポンスヘッダーを以下に定義します。ヘッダーごとに1行で記載しています。

| ヘッダー | 定義 | デモアプリケーションでの使用箇所 |
|---|---|---|
| X-Content-Type-Options | サーバーが宣言したContent-Typeを信頼するようブラウザーに指示する。MIMEスニッフィングを防ぐ。有効な値はnosniffのみ。 | キャッチオールルールによってすべてのURLに適用。/upload/\*には明示的に再適用。 |
| X-Frame-Options | ページをiframe内に表示してよいかどうかを制御する。値DENYはすべてのフレームへの埋め込みをブロックし、クリックジャッキングを防ぐ。 | キャッチオールルールによってすべてのURLに適用。 |
| Referrer-Policy | エンドユーザーがページからリンクをたどる際に、ブラウザーがRefererヘッダーで送信する内容を制御する。値strict-origin-when-cross-originは、クロスサイトの遷移ではオリジンのみ（パスなし）を送信する。 | キャッチオールルールによってすべてのURLに適用。 |
| Permissions-Policy | ページが必要としないブラウザーの機能を無効にする。デモアプリケーションでは、geolocation、camera、microphone、payment、USB、magnetometer、gyroscopeを無効にしている。 | キャッチオールルールによってすべてのURLに適用。 |
| X-XSS-Protection | レガシーなヘッダー。現代のブラウザーは代わりにCSPに従う。値0はレガシーなフィルター（脆弱性の原因となることが知られている）を無効にする。 | キャッチオールルールによってすべてのURLに適用。 |
| Server | サーバーの識別文字列。このヘッダーを上書きすると、クライアントやスキャナーから基盤となるサーバーソフトウェアとバージョンを隠せる。 | キャッチオールルールによって"Sentinel"に設定し、デフォルトの4D/21.0.0という文字列を置き換える。 |
| X-Permitted-Cross-Domain-Policies | Adobe FlashやPDFリーダーがクロスドメインのポリシーファイルを読み込んでよいかどうかを制御する。値noneはこれを無効にする。レガシーだが、設定のコストは低い。 | キャッチオールルールによってすべてのURLに適用。 |
| Content-Security-Policy（CSP） | クロスサイトスクリプティングに対するレスポンス側の主要な防御。スクリプト、スタイル、フォント、画像、フレームを提供してよいオリジンを宣言する。ディレクティブ'none'は、そのリソースの種類についてどのオリジンも許可しないことを意味する。 | ルールによって異なるCSPの値を送信する。ダッシュボードのページにはGoogle Fontsを許可する緩やかなCSPを、APIのエンドポイントにはdefault-src 'none'を適用。 |
| Cache-Control | ブラウザーやプロキシがレスポンスをどのようにキャッシュしてよいかを制御する。値no-storeは保存を完全に禁止する。max-age=Nはキャッシュの有効期間をN秒に制限する。 | 防御対象のほとんどのルールはno-storeを送信。/public/\*は静的リソース用にpublic, max-age=300を送信。 |
| Pragma | レガシーなヘッダー。Pragma: no-cacheは、古いHTTP/1.0プロキシ向けにCache-Control: no-cacheと同じ指示を伝える。 | 多層防御のため、/api/dashboard/\*と /admin/\*で送信。 |
| Access-Control-Allow-Origin | CORS。JavaScriptからレスポンスを読み取ってよいオリジンを宣言する。値\*はすべてのオリジンを許可する。特定のURLを指定すると、1つのオリジンに限定される。 | /api/dashboard/\*ではhttp://127.0.0.1:8044に限定。公開エンドポイントでは\*に設定。 |
| Access-Control-Allow-Credentials | CORS。クロスオリジンのリクエストでCookieやHTTP認証を送信してよいかをブラウザーに指示する。Cookieベースのセッション認証ではtrueにする必要がある。 | ダッシュボードはCookieベースのセッション認証を使用するため、/api/dashboard/\*でのみtrueに設定。 |
| Access-Control-Allow-Methods | CORS。そのルートでサーバーが受け付けるHTTPメソッドを列挙する。OPTIONSのプリフライトレスポンスで返される。 | /api/dashboard/\*ではGET、POST、OPTIONS。/api/public/\*ではより多くのメソッドを許可。 |
| Access-Control-Allow-Headers | CORS。サーバーが受け付けるリクエストヘッダーを列挙する。OPTIONSのプリフライトレスポンスで返される。 | /api/dashboard/\*ではContent-TypeとAuthorization。 |
| Access-Control-Max-Age | CORS。プリフライトの結果をキャッシュしてよい時間（秒）をブラウザーに指示する。 | 600（10分）に設定し、JSONのPOSTのたびにブラウザーがプリフライトを行わないようにする。 |
| Vary | レスポンスが特定のリクエストヘッダーに依存することをキャッシュに伝える。Vary: OriginをAccess-Control-Allow-Originと組み合わせることで、誤ったCORSレスポンスがキャッシュから返されるのを防ぐ。 | /api/dashboard/\*に設定。 |
| X-Robots-Tag | 検索エンジンのクローラーに、URLのインデックス方法を指示する。値noindex, nofollow, noarchiveは、インデックスしない、リンクをたどらない、コピーをアーカイブしないようクローラーに求める。 | /api/dashboard/\*、/admin/\*、/upload/\*、/public/\*、/health、ダッシュボードのページ、ルートURLに適用。 |

## 設定と永続化

### ファイルの配置

実行時の状態はすべて、プロジェクトのDataフォルダーの直下に保存されます。Data/Settingsの下に入れ子にして保存すると、Windowsでパス区切り文字に関するバグが発生したため、これは禁止しています。

| ファイル | 管理元 | 内容 |
|---|---|---|
| Data/dosguard_config.json | ConfigManager | 防御トグル、しきい値、bcryptハッシュ、WAFのパターン。 |
| Data/ip_lists.json | IPManager | ブロックリスト、許可リスト、ストライクカウンター。 |
| Data/Logs/dos_&lt;date>.log | RequestLogger | 日次のJSONL形式のリクエストログ。 |
| Data/sonar_kills.jsonl | Sonar_Sniper_Worker | 1時間ブロックのフォレンジック用の記録。 |
| Data/sonar_archive.jsonl | Sonar_Drone_Worker | パターン相関分析用のアーカイブ。 |
| Data/dos_log.csv | Sentinel.handleExportLogs | ダッシュボードからエクスポートしたCSV。 |

### アトミック書き込みパターン

ConfigManagerとIPManagerはどちらも、書き込み後に名前を変更するパターンを使用します。このパターンにより、書き込み中にクラッシュした場合でも、書きかけのファイルが残ることを防ぎます。

手順は次のとおりです。一時ファイルに内容を書き込み、使用中のファイルを削除して、一時ファイルの名前を使用中のファイル名に変更します。

### ホットリロードの仕組み

ConfigManagerは、ダッシュボードの/api/dashboard/configエンドポイントを通じて、必要に応じて設定を再読み込みします。4Dサーバーの再起動は必要ありません。

HTTPHandlers.jsonとHTTPRules.jsonは、ファイルが書き換えられると4D Webサーバー自身が再読み込みします。RulesManagerとHandlersManagerは、ダッシュボードのためにディスク上のバージョンを追跡します。

## ダッシュボードとフロントエンド

「前提知識」と「動作要件」の条件が満たされたら、Webブラウザーを開き、以下のいずれかのURLにアクセスします。

- http://127.0.0.1:8044
- http://127.0.0.1:8044/sentinel.html

ログインページが表示されたら、パスフレーズを生成して認証し、ダッシュボードにアクセスします。

詳しい手順については、プロジェクトのルートにあるREADMEファイルを参照してください。

### レイアウト

ダッシュボードはhttp://127.0.0.1:8044/dashboard.htmlにあります。インターフェースは4D Webサーバーの静的ファイル用フォルダー内に配置されており、フレームワークを使用しないHTML、CSS、JavaScriptのみで作成されています。

- **ヘッダー**：タイトル、リアルタイムの時計、脅威レベルのバッジ、表示密度のスライダー、テーマの切り替え、ログアウト。
- **テレメトリ**：8つのメトリクスカード。合計、ブロック、レート制限、WAF、許可、ハニーポット、パニックによる拒否、1分あたりのリクエスト数。
- **防御層**：4つのトグルカードとマスタースイッチ。
- **インテリジェンス**：CPUとトラフィックのグラフ、IPブロックリストの操作。
- **オペレーション**：ワーカー、アラート、ハニーポットへのアクセス。
- **コントロール**：パニックの作動、攻撃シミュレーション、Security Equalizerの入口、キーボードショートカット。
- **フィード**：自動スクロールとCSVエクスポートに対応したログの行。

### ポーリング間隔

ダッシュボードは、それぞれ独立したタイマーで4つのエンドポイントを監視します。ブラウザーのタブがバックグラウンドにあるときはリソースの消費を抑えるため、メインのポーリング頻度を5分の1に下げ、ワーカーとハニーポットへのリクエストは完全に停止します。アラートのポーリングは継続し、重要な通知をキューに保持して、タブにフォーカスが戻ったときに即座に表示します。

| エンドポイント | 間隔（表示中） | 間隔（非表示） |
|---|---|---|
| /admin/status | 1秒 | 5秒 |
| /admin/workers | 5秒 | 停止 |
| /admin/honeypot/hits | 10秒 | 停止 |
| /api/dashboard/alerts | 5秒 | 5秒 |

### 認証が必要な場合の処理

JavaScriptのヘルパー関数api(url, method, body)は、次の3つの値のいずれかを返します。

- 成功：解析済みのJSON本文。
- HTTP 401または403：AUTH_REQUIREDシンボル。
- ネットワークエラーまたはHTTP 5xxレスポンス：null値。

AUTH_REQUIREDの場合は、ポーリングを停止してログイン用のオーバーレイを表示します。前のセッションの情報が漏れないよう、ローカルの状態（ログ、履歴）は消去されます。

## ワーカーとプロセスのオーケストレーション

### ワーカーの生成

ワーカーはProcessOrchestrator.spawnによって生成されます。各ワーカーは、オーケストレーター内にハートビート用のスロットを登録します。

各ワーカーは無限ループを実行します。ループの本体では1回分の処理を実行した後、ProcessOrchestrator.sleepによってスリープします。この関数は内部で4D.Signalを使用しています。

### シャットダウン

On Exitは、まずWEB Server.stopを呼び出し、次にシャットダウン用のセマフォに信号を送り、登録済みの各ワーカーに対してKILL WORKERを実行します。

ワーカーはこの信号によってスリープから復帰し、ProcessOrchestrator.shouldShutdownを確認してループを抜け、正常に終了します。

### 稼働状況の報告

各ワーカーは、ループを1回実行するたびに、自分のハートビート用のスロットにタイムスタンプを書き込みます。ダッシュボードは/admin/workersをポーリングし、各スロットの経過時間を各ワーカーの想定間隔と比較します。

ハートビートが想定間隔の3倍より古いワーカーは、ダッシュボードにSTALLEDと表示されます。STALLEDになると、WARNINGレベルのアラートも発行されます。

## まとめ

このデモアプリケーションは、サービス拒否、インジェクション、偵察、ヘッダー攻撃という4つのカテゴリーにわたる標的型の脅威を軽減します。基盤となる脅威モデルは拡張可能なため、開発者はアプリケーションの防御を拡充できます。たとえば、接続のアイドル時間から低速読み取り攻撃を検出する「Slowloris」対策や、TLSレベルのシグナルを侵入検知のスコアリングに取り込むJA4フィンガープリントのチェックを追加することが考えられます。アーキテクチャの面では、このアプリケーションは4D v21.0 LTSの2つの機能に依存しています。HTTPルールによってWebサーバーのすべてのレスポンスにセキュリティヘッダーを適用し、HTTPリクエストハンドラーによって受信したリクエストを独自のクラスへルーティングすることで、ビジネスロジックをルーティング層から切り離しています。
